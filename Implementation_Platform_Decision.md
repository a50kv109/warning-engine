# IMPLEMENTATION PLATFORM DECISION — WARNING ENGINE v1.0

## Executive Summary

Цель данного документа — выполнить объективную инженерную оценку и утвердить платформу реализации для проекта **WARNING ENGINE v1.0**. 

Архитектура WARNING ENGINE требует строгого соблюдения принципов (Pure Functions, Stateless Processing, Deterministic Behaviour), реализации SOL-примитивов (SOURCE, CONSTRAINT, FLOW, COMPARE, STATE) и жесткого следования Data Contracts. Выбор платформы определяет, насколько естественно эти архитектурные требования будут переведены в исполняемый код, а также насколько легко система будет интегрироваться с AI-агентами экосистемы E-OS.

## Compared Platforms

Для анализа выбраны три основные платформы:

1. **TypeScript / Node.js**
   * **Особенности:** Строгая структурная типизация, функционально-ориентированный дизайн, нативная работа с JSON-структурами.
   * **Специфика:** Идеальное совпадение форматов данных с веб-экосистемой и API LLM-агентов.

2. **Python**
   * **Особенности:** Стандарт де-факто для аналитики и Data Science, лаконичный синтаксис.
   * **Специфика:** Динамическая типизация (требует дополнительных инструментов вроде `mypy` и `pydantic` для обеспечения строгих контрактов).

3. **Go**
   * **Особенности:** Высокая производительность, статическая типизация, минимализм, компиляция в единый бинарный файл.
   * **Специфика:** Многословная обработка ошибок, слабая экосистема для прямой интеграции с высокоуровневыми AI-фреймворками по сравнению с TS/Python.

## Engineering Recommendation

Проведя анализ, **TypeScript / Node.js** определяется как наиболее подходящая платформа для реализации WARNING ENGINE v1.0.

**Инженерное обоснование:**
1. **Data Contracts:** TypeScript обладает мощной структурной типизацией, которая позволяет описать `WarningResult`, `Predictor` и `Thresholds` максимально точно. При использовании библиотек валидации (например, Zod) обеспечивается 100% гарантия совпадения контрактов в runtime и compile-time.
2. **AI-Ready:** LLM-агенты и инструменты экосистемы нативно оперируют JSON-объектами. TypeScript стирает границу между типами данных приложения и контрактами API (в отличие от Go и Python, где требуется маршалинг/демаршалинг).
3. **Stateless & Pure Functions:** Функциональная парадигма TypeScript идеально ложится на заявленные принципы `Pure Functions` и `Stateless Processing`. SOL-примитив `FLOW` естественным образом реализуется как цепочка чистых функций (pipeline).
4. **Универсальность:** Инфраструктура позволяет запускать движок как в контейнерах, так и в serverless-средах (Edge), что дает максимальную гибкость.

## Selected Technology Stack

- **Runtime:** Node.js (v20+)
- **Language:** TypeScript (Strict Mode = true)
- **Data Validation:** Zod (для Runtime-валидации CONSTRAINT-примитивов и Data Contracts)
- **Testing:** Vitest / Jest (для проверки детерминированности Pure Functions)
- **Package Management:** npm / pnpm

## Consequences for Repository Structure

Выбор TypeScript модифицирует ранее обсуждаемую физическую структуру дерева (переход от Python-паттернов к Node-паттернам). 
Ожидаемая физическая структура:
- Замена `pyproject.toml` на `package.json` и `tsconfig.json`.
- Замена директорий модулей с `__init__.py` на `index.ts` (Barrel-файлы).
- Точка входа в кодовую базу: `src/index.ts`.

## Consequences for Generated Documentation

- В `ARCHITECTURE.md` и `API_REFERENCE.md` все Data Contracts и Extension Points будут описываться в терминах TypeScript-интерфейсов (`interface`, `type`).
- В `CONTRIBUTING.md` и `DEVELOPMENT.md` процессы установки будут базироваться на `npm install` и скриптах сборки `npm run build`.
- В `MANIFESTO.md` и `AGENTS.md` необходимо будет зафиксировать использование экосистемы TS для обеспечения строгой типизации контрактов.
